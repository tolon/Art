### 7. ✅ `.vhd` output beside `.img`, and saying what a file is · *done 2026-08-24*

A 32 GiB card image costs 32 GiB today. Now with evidence beyond "the imager
offers it": the owner's `AmiKit.hdf` is 1 200 776 704 bytes beginning
`conectix` — a **dynamic VHD wearing an `.hdf` extension**, which is what one
shipped distribution hands its users. Two halves: ART should **write** a
`.vhd`, and `core/detect` should **say** a `.hdf` is really a VHD rather than
mis-reading it as a hard-disk image.

**Half two done 2026-08-24.** `core/vhd.rs` reads the 512-byte footer — the
format checked against libyal's `libvhdi` documentation, VirtualBox's
`VHD.cpp` and Microsoft's own notes rather than recalled. Detection looks in
**two** places because the specification puts the footer in two: a dynamic or
differencing image keeps a copy at offset 0, a fixed one only at the end.

**The two kinds get two answers, and that is the design.** A *fixed* VHD is a
raw image with 512 bytes appended, so every ART reader works on it unchanged
and it keeps every offer an ordinary image has. A *dynamic* one does not store
its data at offset 0 at all, so it is kept away from the Hard Disk Studio and
WinUAE — the same narrowing `is_lha` makes inside `is_archive`, and for the
same reason: an action that exists to fail (§46, §89). **It would have failed by
saying "this hard disk has no partition table"** about a disk that has one —
true about the bytes at offset 0, wrong about the disk. Hex and Collection
stay, so it is not a dead end (§91): hashing works whatever is inside, and raw
bytes are what somebody looking at an unopenable container wants.

The checksum is computed and **reported, never used to reject**: ART has one
real VHD to check the arithmetic against and it belongs to the owner. A
permanent `#[ignore]`d hook (`ART_VHD_IN`) is what will settle it.

17 tests. Nine mutations, nine fell — fixed and dynamic transposed, every kind
claimed to start at offset zero, the checksum no longer skipping its own field,
the length check weakened, little-endian instead of big, a fixed footer at
offset 0 accepted, the whole check skipped, the raw-studio narrowing removed,
and a fixed VHD narrowed along with the others.

**Half one done too, 2026-08-24, and the premise was measured first.** The
item said a 32 GiB card image costs 32 GiB; `build_card`'s own doc comment said
the opposite (*"`set_len` on NTFS costs nothing and takes no space"*).
`SetLength(2 GB)` on the owner's NTFS consumed **exactly** 2 147 483 648 bytes
and `fsutil` said the file was not sparse, so the item was right and the
comment was [ART-230](../../ISSUES.md).

`core/vhd/write.rs` writes a **dynamic** VHD — chosen over marking the file
sparse because `FSCTL_SET_SPARSE` is a Windows API call `core/` may not make,
and because a VHD's saving survives being copied to another machine where
NTFS sparseness does not. A destination ending `.vhd` gets one; anything else
is still the raw image every card writer takes, and **both go through one
`lay_out`**, so the two cannot drift apart in what they write.

`read_card` understands one too — without that, §92's VERIFY step would have
been verifying nothing.

**Verified by something that is not ART**, which is `core/card/build`'s own
rule: `scripts/vhd-oracle-check.py` writes an image and reads it with
Microsoft's `Get-VHD` and `Test-VHD` from the Hyper-V module. Every field
agrees — VhdType Dynamic, Size 34 359 738 368, FileSize **6 360 576**,
BlockSize 2 097 152 — a **5 402×** saving. Not in CI: the module is not on a
GitHub runner.

Eight mutations, five fell at once and **three survived**, all three because a
test was missing rather than because the code was safe: a second write to an
already-allocated block landing on its own sector bitmap, `open` accepting a
fixed image, and the block-count bound. All three now have one, and all three
fell on the re-run.

### 11. ✅ ART-130 — offer the Kickstart a game asks for · *done 2026-08-24*

Decided 2026-08-21: yes, in its own round, and **always as a proposal** —
*"this title asks for `kick34005.A500`; ART recognises it in your collection —
place it?"*, never a silent copy. Sits next to the games side rather than
before it.

**The matching half is built.** `RomInfo::whdload_crc16` is computed at

One of three alternatives is enough, which is ART-137's lesson applied.

**Nothing in `offer.rs` writes a file**, and a test shows that rather than the

**The placing step and its screen landed the same day.** `core/rom/place.rs`
carries out one agreed placement — never a title's worth. The name comes out of

rather than replaced. The screen sits in `TitleDetail.tsx` beside the sentence

one instead of offering a button that cannot work.

### 12. 🟡 SD-2 G10 waves 2 and 3 — launcher metadata · *the format is
built; where it goes is now a measured question*

Wave 1 (the game index) landed 2026-08-17. Wave 2: `igame.data` beside each
slave, drawer extraction from a hardfile, `games.json`. Wave 3: AGS export.
This is the last gap SD-2 names.

**The format is built and verified against iGame's own source**
(`core/gameindex/igame.rs`, 2026-08-24). `MrZammler/iGame`'s
`fsfuncs.c::getIGameDataInfo` and `funcs.c`'s calls to it were **read**, and
five of the six rules would have been got wrong by writing what the format
looks like from the outside — each producing a file iGame silently ignores:

- **the line buffer is 64 bytes**, and a longer line is *split* rather than
  truncated, so the tail arrives as the next line where an `=` inside a long
  title is parsed as a key;
- keys are matched with `strcmp`, so exactly lower case;
- **nothing is trimmed** — `title = X` yields the key `"title "`;
- `year` and `players` are taken only when `isNumeric`;
- **`exe` is rejected when it contains `.slave`**, which is the trap, because
  the obvious thing to put there is the slave.

An existing file is **edited, not regenerated** (CLAUDE.md's config rule: iGame
ignores unknown keys, so a user may keep their own in it), and a value that
will not fit is left out and **named** rather than shortened. 15 tests; eight
mutations, eight fell.

**But "beside each slave" cannot be done for this owner's collection, and that
is measured rather than argued.** Counted over their own catalogue on
2026-08-24: **2 815 titles — 1 697 `whdload-hardfile`, 1 016 `floppies`, 102
`hardfile`, and zero drawers.** `Media::WhdloadDrawer` was removed by
[ART-147](../../ISSUES.md) because the shape was wrong. The slaves are
**inside** the hardfiles.

So the remaining work is not "write the file", it is one of two routes, and
neither is built:

1. **into the hardfile**, beside the slave, through `core/volume/write` — a
   `whdload-hardfile` is a bare FFS volume ART can already write.

   **Measured before anybody decides**, on all 1 697 of the owner's own images
   (`igame::free_bytes_in_hardfile`, read-only): **every one read without
   error**, the median has **43 008 bytes free** against a file of a few dozen
   bytes, and **148 have less than a kilobyte** — many exactly zero. So the
   route is open for about **1 549** titles and closed for **148**, which is a
   distinct ending rather than a failure.

   **It is still a decision, not a task**: this writes into somebody's game
   files. It wants the same shape ART-130 got — a proposal, a confirmation and
   a backup policy — and the owner's word before any of it.

   **Asked, and the answer parks it: the owner does not use iGame**
   (2026-08-24). So the route has no reader today.

   **And when it does have one, it is not a bulk operation.** The owner's own
   words: *“igame kullanacak olsam bile 1000 tane dosyayı taşımana gerek yok, 5
   tane dosya taşısan yeterli.”* Nobody plays 1 697 games; they want a handful
   to look right in the menu. So the shape is **one title at a time, the one
   the user picked** — ART-130's shape — and an *apply to all* button is not
   the default and probably not wanted at all. That is a design constraint on
   this route, recorded before anybody builds it. The format module stays,
   verified against iGame's own source and tested, for whoever does — but
   nothing writes into a hardfile until somebody wants the result, and *"build
   it in case"* is not a reason to touch 1 697 of somebody's files.

   **A standing rule came out of the same exchange**: an experiment that
   *writes* to the owner's collection is run on **three to five copies**, never
   on the originals. Read-only measurement over the whole collection is fine —
   the free-space run above touched nothing, which was verified twice: the
   reading half of `core/volume` uses a plain `File::open` and a separate type
   (`FileRegionMut`) is the only one that can write, and afterwards not one of
   the 1 697 images had a modification time newer than 2024-01-30;
2. **into a distribution's own Games drawer**, for a build that unpacks WHDLoad
   archives rather than carrying self-booting images — the ClassicWB/HstWB
   shape, which this collection is not.

Drawer extraction from a hardfile, `games.json` and the AGS export are
untouched.

**One number worth carrying elsewhere**: **966 of the 2 815 titles declare a
Kickstart**, which makes [ART-130](../../ISSUES.md) — finished the same day —
apply to a third of the collection rather than to a handful.

### 13. 🟡 SD-3 G14 — it is *mine* · *the network half's core landed 2026-08-24*

Wallpaper, WiFi, prefs and Startup-Sequence, **each edited in place** — the
config-files-are-user-data rule, applied to the Amiga side. The WiFi PSK must
stay out of the operation log, the manifest and any AI prompt. Wallpaper is
new scope and should be scoped before it is built.

**Startup-Sequence was already done** — `core/osinstall/startup.rs` edits
`S:User-Startup` in place with the `;BEGIN`/`;END` convention real Amiga
installers use, and 2026-08-24's keymap selection is its first real user.

**The network half's core is built: `core/amiganet/`.** And the file it writes
is **not** the one a recalled answer would have named. `DEVS:NetInterfaces` is
Roadshow's; this owner's stack is their own, and they pointed at the source:

| | file | holds |
|---|---|---|
| `tolunwifi` | `ENVARC:Sys/Wireless.prefs` (+ `ENV:` twin) | the credentials — **the secret** |
| `tolunnet` | `DEVS:tolunnet.config` | device, unit, DHCP or static |
| Roadshow | `DEVS:NetInterfaces/<name>` | what ART would have written, wrongly |

Both formats were read out of their own C, and **the two neighbouring formats
have opposite rules**: `igame.data` compares keys with `strcmp` and
`tolunnet.config` with `str_equal_nocase`. Only reading tells you which is
which. Other things a look at the shape would have got wrong: a WPA block
carries **no `key_mgmt` line** (the supplicant defaults to WPA-PSK when a `psk`
is present); a passphrase is quoted and a 64-hex PMK is **never** quoted;
`scan_ssid=1` on every form except the hashed one; `tolunnet` accepts aliases
(`GW`, `MASK`, `NAMESERVER`…) so a rewrite that only knew the primary spelling
would leave the user's old value winning; and a `tolunnet` value stops at the
first space, so one containing a space is silently truncated on the Amiga.

**The PSK is a type, not a rule.** `Secret` deserialises and does not
serialise, so a profile cannot reach the operation log, a manifest or an AI
prompt through `serde` at all, and `Debug` prints stars. G14 asks for that as a
rule kept in three places; this makes it a compile error.

32 tests. Ten mutations, ten fell. **Two real defects came out of the tests**:
an index-out-of-bounds in the config rewriter — a variable-length list indexed
by a fixed key order, which panicked the moment a DHCP configuration met a file
with a `DNS=` line — now unrepresentable rather than checked; and one of the
assertions was failing for the wrong reason, because the value under test was a
substring of the sentence.

**The screen and the placing landed the same day**, on the owner's answer:
*"ART sorsun, kart kurarken WiFi bilgilerini girelim."* `core/amiganet::seed`
puts the two files into a system volume — `tolunnet.config` **merged**, because
the stack's own preferences GUI writes it too; `Wireless.prefs` **replaced**,
because merging two lists of networks means deciding which of somebody's to
keep, which is a decision rather than a merge. The count of what is already
there is fetched when the tree is known and shown **above** the button, never
after it.

`NetworkPanel` sits on the volumes step beside the panel that writes the card,
because that is when somebody is setting one up.

**One deliberate exception to ART's own remembered-settings rule, and it is
proven rather than described**: the passphrase is *not* remembered. Everything
else on the panel is — the SSID, the driver, the address — but a WiFi password
in ART's settings file is a WiFi password in a file nobody thinks of as a
secret. The field says so, and a test asserts it is absent from the settings
bag before and after a write and that the field is empty afterwards.

Eight mutations on the panel, eight fell; six on the seeding, six fell after
one was covered — the survivor counted `network={` blocks by looking for the
word `ssid`, which is right until a file carries a comment mentioning it, and
the number is shown to somebody as *"you are about to replace N networks."*

**Wallpaper is dropped**, 2026-08-24, by the owner: *"duvar kağıdını boşver,
kullanıcı onu kendisi yapar."* It was the one part of G14 that had no home in
any existing document, and the answer to *"should it be scoped?"* turned out to
be no. Nothing to build.

**And the WiFi half shipped with a real defect that was fixed the same day** —
[ART-231](../../ISSUES.md): `ENVARC:` is an **assign**, and ART wrote to a
drawer called `Envarc` rather than to `Prefs/Env-Archive`, which is a card that
comes up with no network and no error. Every test around it built its expected
path from the same constant, so the suite agreed with the mistake.

**The rest of G14's table was assessed rather than built, and the evidence is
the owner's own trees.** Not a refusal — a recommendation they can overturn.

| Input | What measuring found |
|---|---|
| Wallpaper | **Dropped by the owner**, 2026-08-24 |
| Keymap | **Done** — `SetKeyboard` in `S:User-Startup` ([ART-226](../../ISSUES.md)) |
| WiFi | **Done** — `core/amiganet` |
| Startup-Sequence | **Done** — `core/osinstall/startup.rs` |
| Timezone | `locale.prefs` **already exists** in a freshly installed tree and already carries `Türkiye`. The OS install writes it; ART would be overwriting a correct file |

| Screen mode, overscan | `screenmode.prefs` and `overscan.prefs` are **absent** from a fresh 3.9 tree: they exist only once somebody opens the editor. A wrong screenmode is a card with no picture |

So what is left of G14 is: **two binary formats ART cannot verify, for two

### 14. 🟡 SD-3 G16 — multiboot · *the card half done 2026-08-24*

Several complete environments plus a boot menu. Also the home of a named
ROM+volume pairing, deferred here by G9.

**There is no menu to write**, which is the thing a design would get wrong
first. AmigaOS already has one: hold both mouse buttons at power-on and the
Early Startup screen lists every bootable partition. What ART decides is which
one starts when nobody holds anything, and that is `de_BootPri` — *"suggested
value zero"*, **higher boots first** (ADCD 2.1's *RigidDiskBlock and Alternate
Filesystems*, read 2026-08-24).

**The card format always allowed three Amiga disks and the builder could only
ask for one.** `core::mbr` writes them and `read_card` opens real cards that
have them; `card_spec` hard-coded a single `AreaSpec`. `CardBuildRequest` now
carries `extra_disks`, and `first_disk_bytes` for when there is something after
it — reusing `plan_card`'s own rule that only the **last** disk may take what
is left, rather than restating it. A test caught that `card_plan_build` had its
own hard-coded `&[0]`: two places decided how many disks a card had, and
changing one left the plan showing a single area.

**A tie is named, never resolved** (`core::card::multiboot`). What happens when
two bootable partitions share a priority is not documented anywhere, so ART
says which are tied — a card whose two systems are both *"first"* is a card
whose owner does not know which they are about to boot. The check looks at
**every disk at once**, because the ordinary way to build this wrong is two
systems on two disks both left at the priority a single-system card uses.

Every disk gets the drivers the user supplied — [ART-097](../../ISSUES.md)'s
lesson applied to a card ART *builds* rather than one it reads.

9 tests in `multiboot.rs`, 5 at the command level. Nine mutations, nine fell —
two only after being covered: a single extra disk saying `0` cannot tell a
sized disk from an unsized one, and nothing asserted the drivers reached the
second RDB, which is exactly what ART-097 was about.

**The screen landed the same day.** Power User only: one checkbox and one
number — how big the **second** AmigaOS is, since that is the thing being
added. The first disk states its size and the second takes what is left,
because the planner allows *"the rest"* only for the last disk, so the sector
rounding lands on the disk whose size somebody typed as a round number rather
than on the remainder. Priority **0** against the first's **1**, which is what
`defaultPartition`'s own note already left room for. One partition per extra
disk, spanning it: a second environment is a second *system*, not a second work
volume, and offering a split would be offering a shape with nothing behind it
(§96) — the same reason the first disk has a toggle rather than an editor.

A refused split is refused **on the screen**, not silently downgraded: the
fields are left off the request so nothing half-split is planned, and the
sentence blocks Build. That mattered — a refused split leaves a perfectly good
one-disk card, which plans successfully, so without the block a card asked for
with two systems would have been built with one.

[ART-233](../../ISSUES.md#fixed) was found on the way, and it is this project's
own favourite shape: `AmigaDiskRequest` carried a camelCase rename its
neighbours do not, so `size_bytes` would have arrived as an unknown field and
defaulted to 0 — *"take the rest"* — turning an 8 GB second system into the
whole remainder without an error. Never reachable by a user; found by the first
thing that sent one.

Ten more mutations, ten fell. One only after being rewritten: the refusal's
sentence is rendered twice, and "Build is disabled" passed while no plan
existed at all, so dropping the refusal's precedence left every test green.

**The pairing G9 deferred here was examined on 2026-08-24, and what shipped is
not what it asked for.** G9 deferred *"a named, stored, reusable pairing of ROM
+ volume + Emu68 config"*, on the reasoning that multiboot *is* several ROMs and
several volumes. Checked against how a card actually boots, that shape does not
hold: **the Pi firmware reads one `config.txt`.** There is no boot-time chooser
for the Pi side at all — the `config_<name>.txt` sets are alternates you
*activate*, which rewrites the file. So a stored triple would be an object with
nowhere to be used.

What was missing is the check at the moment the choice is actually made.
`core/pistorm/activation.rs` reads what a set names and says what activating it
*means*: which Kickstart the Amiga will load, which kernel the Pi will boot,
and — the one that matters — whether either of them is **on the card at all**.
That is [ART-103](../../ISSUES.md#fixed) reached by a different road: ART-103
was ART writing a kernel name no release carries, and this is a user activating
a set that names a file which is not there. Both fail on the Amiga, where ART
cannot see it, with nothing wrong on screen beforehand — the preview was a text
diff, and one changed character is what the difference looks like.

It refuses to guess where the format says it cannot know: a `config.txt` with
`[gpio…]` stanzas chooses its kernel from the board at boot and its `initramfs`
is a firmware rather than a Kickstart ([ART-204](../../ISSUES.md)), so ART says
*that* and names nothing.

**Still open, and narrower than it was:** which *volume* a set is for. ART now
knows the ROM and the kernel a set names; it does not model "this firmware set
goes with that system partition", and nothing on a card records it.

### 15. 🟡 SD-5 G13 — capacity planner and build profiles · *the safety half
done 2026-08-24*

Comfort, and honestly placed after the things that change what ART can do.

**Except one half of it was not comfort at all.** Opening the item found that
ART would happily build a **20 GB FFS partition**, and `core::rdb` knew a card
may hold at most 32 partitions and **nothing about how large one may be**. On a
Kickstart 3.1 machine the original FFS does not refuse a partition past its
4 GiB addressing — it writes past it and *"causes serious data corruption all
through the drive"*.

**The limit is not FFS's; it is the FFS on the machine**, which is what makes
this worth writing carefully. Read rather than recalled (Wikipedia's *Amiga
Fast File System* version table, classicamiga's large-drive guide, the AmigaOS
wiki on TD64 and NSD): the original FFS stops at ~4 GB, **v45** (3.5/3.9, on
disk) uses NSD, and **v46+** (3.1.4/3.2, in ROM) supports TD_64 and NSD
natively. So the question needs the card's Kickstart — which ART has, since
[ART-223](../../ISSUES.md) made the build carry one ROM.

**It warns and does not refuse**, and the reason is that ART cannot see
everything that lifts the limit: a 3.9 system loads v45 from disk and
`SetPatch` replaces the ROM's filesystem at boot. So the sentence names the
condition instead of pronouncing a verdict — and *"no Kickstart chosen"* gets
its own sentence, because it is not the same as *"an old one"*.

PFS3 and SFS carry their own filesystem in the RDB and are left alone; warning
about them would push somebody off the filesystem the PiStorm card path
actually uses.

13 Rust tests. Six mutations, six fell.

**Still open:** the planner proper — *"pick a profile, see the proposed volume
table scaled to the card, adjust, go"*. The registry half landed 2026-08-13 and
every entry is `available: false` pending a real download read by hand.
