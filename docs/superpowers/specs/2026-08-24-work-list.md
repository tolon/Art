## The sequence

Ordering principle, stated so it can be argued with: **finish what is already
half-open before starting anything new; prefer the thing that makes an
existing claim honest over the thing that adds a claim.** Size is a rough
half-day / day / week, not a promise.

### 1. ✅ ART-227 — the BoingBag fix-ups after the `Updater` · *done 2026-08-24*

ART runs a BoingBag's own `Updater` exactly as HstWB does and then stops.
HstWB does seven more things, and one of them moves
`Devs/AmigaOS ROM Update.BB39-2` (321 768 bytes, measured in the payload) over
the old file. Nothing ART has claimed is false; the install is incomplete.

**First, the measurement this entry owes**: install BoingBag 2 through
`real_install_hook::install_a_real_package_when_asked` and list `Devs/`, so
the before-state is on record rather than inferred. Then the fix, as **typed
operations in the package recipe** — *protect*, *copy-if-target-exists*,
*rotate-aside-then-replace*, *run-if-library-older-than* — never free-text
AmigaDOS, which would drive a hole through `startup_sequence`'s
metacharacter refusal. A failed fix-up needs its own ending; it is not the
installer failing.

**Done when** a BoingBag-2 install leaves `Devs/AmigaOS ROM Update` as the
321 768-byte file, the old one beside it under a backup name, and a real run
says so.

**Progress 2026-08-24 — the measurement half is done and the item is bigger
than *day*.** Both BoingBags were installed on a fresh copy of a pre-BoingBag
tree (BB1 170.7 s → 3 859 files, BB2 138.1 s → 3 868 files / 20 533 434 bytes,
byte-identical to the run recorded on 2026-08-21), and `Devs/` afterwards
holds `AMIGAOS ROM UPDATE` at **127 956 bytes** — the CD's own, still the one
`SetPatch` loads — beside `AmigaOS ROM Update.BB39-2` at **321 768**, inert.
Confirmed, not inferred. The protection bits are measured too: none of the
seven commands HstWB sets `+prwed` on has the `p` bit after ART's BB1, which
also settles the alternative — the `Updater` does not do these itself.

**Why it is bigger: `AmigaOS ROM Update` has spaces in its name and
`core/amigainstall` cannot currently express that.** Its module documentation
refuses `"` on purpose and refuses whitespace in composed values with it. The
resolution is in [ART-227](../../ISSUES.md#open) — quote fields ART itself
defines as paths, never an installer's own arguments — but it means touching
the script generator's safety surface, adding a `RunOutcome` variant for a
failed fix-up, and a schema change in the package recipes. Re-size: **two to
three days**, not one.

**Done the same day after all, and the re-size is why.** Moving the work to
the host — `core/amigainstall/finish.rs`, applied against the staged copy
between a successful run and `settle` — made both of the expensive halves
disappear: no quoting problem, because these are ordinary file operations, and
no fifth `RunOutcome`, because a failure is a `CoreError` raised before
anything is promoted. Verified end to end on the owner's material: BoingBag 1
169.1 s reporting all ten protection steps, BoingBag 2 138.0 s reporting the
rotation, and `Devs/AmigaOS ROM Update` is now the 321 768-byte file with the
one it replaced kept at `.old`. Seven mutations against the new module, all
seven fell.

### 2. 🟡 ART-226 question 3 — the same keymap hole in the AmigaOS 3.2 recipe · *keymaps done 2026-08-24; the fonts half became [ART-228](../../ISSUES.md)*

3.9 got its `keymaps` component on 2026-08-24. 3.2's `storage` component
places `Keymaps → Storage/Keymaps` and nothing copies any into `Devs/Keymaps`,
so a 3.2 tree has the identical defect. Unverified — that is the first step,
not an assumption.

Also measured and owed here: the owner's `Locale-TR.adf` carries
`Support/Fonts/topaz_iso-8859-9` and `SevenAlone_iso-8859-9`, and the `locale-tr`
component does not place them. That is [ART-159](../../ISSUES.md#fixed)'s
defect in the other recipe — Turkish catalogs with no Turkish glyphs.

**Done when** a 3.2 tree built from the owner's ADFs carries the keymaps and
the ISO-8859-9 fonts, measured by the existing real-media hook.

**Half done, and the other half turned out to be a different problem.** The
keymaps are in: a `keymaps` component naming the shelf's twenty-two files,
verified against both of the owner's ROMs (V40: 29 components, 3 976 files,
12 751 572 bytes; V47: 28, 3 972, 12 702 052), 0 refusals, and the twenty-two
good icons left alone.

The fonts are **not**, and chasing them found [ART-228](../../ISSUES.md):
`Locale-TR.adf`'s `Support/Fonts` is compressed, like **3 263 other files in
every 3.2 tree ART builds** — the whole help system included. The release's own
Installer decompresses them and drops the `.Z`; ART copies them verbatim.
Placing the fonts before ART can decompress would put unusable files on the
volume, so that half waits for ART-228 rather than shipping something that
looks done.

### 2a. ART-228 — decompress what the release decompresses · *day*

Jumped the queue because item 2's second half cannot be done without it, and
because it is the largest correctness gap now open: **3 263 files** in every
3.2 tree ART builds are `compress`-format `.Z` under the wrong name, where the
release's own Installer writes them decompressed. The whole help system, in
every language, plus the Turkish fonts and catalogs.

Needs an LZW `compress` reader beside the other read-only decompressors in
`core/archive`, applied by `apply` when a source name ends `.Z`. One decision
is the owner's: whether the manifest records the medium's own name and hash
beside the placed one, or says nothing.

**Done when** a 3.2 tree carries no `.Z` where the Installer would have
carried none, and a decompressed catalog matches what the Amiga would read.

### 3. 🟡 ART-226 question 2 — `Locale3_9.lha` as a package · *wholesale half done 2026-08-24*

The official 3.9 Locale update, which the owner already has, carries 49
keymaps against the CD's 22, `türkiye.country`, a 2 520-byte
`türkçe.language`, both flags, a Providers entry and **15** Turkish font
families (a strict superset of the CD's 13). It is an archive, not install
media, so it is a **package** in ART's vocabulary.

**The open question is catalogue shape**, not mechanism: one `locale-3.9`
package, or a Turkish slice of one. Decide against the same rule the recipes
follow — a fourth package is a JSON file, not a code path.

**Answered by the archive rather than chosen.** Its own installer asks which
of twenty languages the user wants and then splits its work: `Locale/Flags`,
`Locale/Providers`, `Locale/Languages`, `Devs/Keymaps`, `L` and
`Devs/Printers` go in **wholesale**, while `Locale/Catalogs/<lang>`,
`Locale/Help/<lang>`, `Fonts/<lang>` and `Libs/<lang>` go in **per language**.
So the wholesale half is one package and it is built: `locale-39`, six subtree
rules, verified against the owner's own archive — 0 refusals, 239 plan items,
and `Devs/Keymaps` holding **49** keymaps against the CD's 22 with `türkçe`
among them. Four mutations, all four fell, including the one only real
material can answer.

**The per-language half is not built**, and it is a catalogue-shape question
ART's model cannot answer today: one package per language, or a package that
takes a language as a parameter. Shipping twenty languages' content because
somebody wanted one would be ART answering a question the release asks.

### 5. ✅ Name a disc against a table ART can stand behind · *done 2026-08-24*

What survives of the 2026-08-22 list's item 4 after ART-222 closed and the
186-row Escom hash table was dropped (the owner's media is 3.2 and 3.9, not
the defective 3.1 pressings). ART should be able to say *which* AmigaOS
release a disc or disk set is, from content, and say nothing when it cannot.

**There is no table, and that is the answer to the item's own title.**
`core/osinstall/identify.rs` reads every name out of `recipe::by_release` at
call time — a recipe already declares each component's `media` (the volume
name **inside** the image) and whether it is `required`, and both are checked
against the owner's real discs by the plan tests. A future release stays a JSON
file and teaches this module its media for free. Nothing is hashed: HstWB
identifies each disk by MD5 as well, which is stronger evidence ART cannot
carry, because a hash table is a claim about pressings nobody here can check.

**It found a live defect on the way in, [ART-229](../../ISSUES.md).** The
existing `recipe::release_holding` counted any matching volume name as proof,
and `Fonts` and `Locale` carry no version suffix in *any* of 3.1, 3.1.4 and 3.2
— verified against HstWB's `amiga-os-entries.csv` and two 3.1 installation
guides. Measured before the change: `["Workbench3.1", "Fonts", "Locale"]`
answered `Some("AmigaOS 3.2")`, on a screen that offers a one-click release
switch on the strength of it. All four measured cases now answer `None`, and
the six ART-208 tests pass unchanged.

**What is built and deliberately not on screen.** `MediaVerdict` also carries
`missing_required`, the `Ambiguous` candidate list and `Unknown`'s
`shared_only`. The first reaches no screen because the install step already
renders a `MediaMissing` refusal per component from the plan, and a second
sentence about the same absence is what this project's "one question, one
implementation" rule (ART-203) exists to prevent. The other two are what the
command's `Option<String>` collapses to *silence*, which is the correct screen
behaviour and is now reached for the right reasons rather than by accident.

19 tests. Eight mutations, seven fell; the eighth survived and is disclosed in
ART-229 — it pointed at a test whose name promised a property that a different
line of code actually holds up.
