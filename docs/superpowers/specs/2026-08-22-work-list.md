## The data tables, and what they settle

The imager's inputs are a **published Google Sheet**
(`12UcKD7INDH9y7Tw_w1q3ebQOUS9JtARIs8Z9JWfLUWg`), one tab per table, fetched at
run time. That is why they are not in its repository and why it needs internet.

Three were read:

**`DiskDefaults` — the authoritative default layout.**

| Partition | Device | Volume | Buffers | MaxTransfer | Mask | DosType | Bootable | Priority |
|---|---|---|---|---|---|---|---|---|
| System | `SDH0` | `Workbench` | 300 | `0xffffff` | `0x7ffffffe` | `PFS\3` | TRUE | 1 |
| Work | `SDH1` | `Work` | 300 | `0xffffff` | `0x7ffffffe` | `PFS\3` | FALSE | 99 |
| boot | `SD0` | `EMU68BOOT` | — | — | — | FAT32 | — | — |

**`FileSystems` — handlers identified by MD5**, e.g. `PFS\3,PDS\3` →
`Pfs3aio`, *"PFS (AIO) 19.2"*, `2912D39E…`; `DOS\7` → *"FFS 47.4 (OS 3.2)"*,
`ED36A474…`.

**`InstallMediaHashes` — 186 rows** of known-good install media: MD5,
`ADF_Name`, `FriendlyName`, **`ADFSource`** (`Cloanto`, …) and a `TypeofCheck`
of either `Hash` (the whole file) or `FileCheck` (named files *inside* the
image, extracted with 7-Zip `-ir!`). Several ADFs have **more than one**
accepted hash.

**The pattern, and it is the one worth taking:** everything the tool consumes —
ROM, ADF, ISO, LHA, filesystem handler — is identified **by content against a
published table**, never by filename. ART already does exactly this for
Kickstart ROMs (154 dumps from amitools' Remus data, re-verified in CI). The
gap is ADFs and filesystem binaries.

## The list

### 1. ✅ [ART-204](../../ISSUES.md) — `config.txt` sections. **Done 2026-08-22.**

Measured: the real Emu68 `config.txt` through `merge_config_txt` returns **one
`kernel=` line out of four**, in the stealth stanza, leaving three board
stanzas with none. This is a sufficient explanation for *"no card ART built has
ever been flashed or booted"*.

Fix: key the written-set on `(section, key)`. **One decision belongs to the
owner first** — when the archive already names a kernel per board, ART should
probably not rewrite `kernel=` at all.

### 2. ✅ [ART-203](../../ISSUES.md) — a tree cannot be built from the screen. **Done 2026-08-22**, and a tree has since been built from the screen: 1146 files into `E:\amiga\Amigatolon\os39\art5`.

`apply` refuses every folder that exists; the folder picker can only return one
that does. Measured on the owner's machine. Proposed fix: accept an existing
**empty** directory, refuse a non-empty one — `packagevol::unpack` already uses
that idiom one module over.

### 3. ✅ [ART-196](../../ISSUES.md) — scratch on `C:`. **Done 2026-08-22.**

It was **eighteen** call sites, not one. `crate::scratch` holds one root; a
`core/` function that stages takes the directory; a chosen root that cannot be
reached **refuses** (`ART-SCRATCH-UNAVAILABLE`) rather than falling back to
`C:`. Asked once on first run with *use the system drive* as the first
button's answer, a Settings entry too, and changing it moves nothing.
`scripts/scratch-root-sweep.py` fails CI on the nineteenth call site.

**Also closed on the way, and not on this list when it was written:**
[ART-205](../../ISSUES.md) — the plan predicted 18% more bytes than landed
whenever one component overrode another. Plan and tree now agree exactly on
both of the owner's own releases (3.9: 14 883 492 = 14 883 492; 3.2:
12 700 698 = 12 700 698).

## Where the list stands (2026-08-22, evening)

Items 1–3 are closed. **What is left, 4–12, splits into two groups**, and the
split matters more than the numbering:

- **On the critical path to a card that boots** — 6 (default layout) and 7
  (`cmdline.txt`). Item 1 was *"a sufficient explanation for no card ART built
  has ever booted"*; these two are the rest of the same file's family, and the
  bar for 1.0 is hardware.
- **Everything else** — 4 (identify media by content), 5 (an RDB note), 8
  (`.vhd`), 9 (more recipes), 10 (the catalogue as data), 11 (OS Builder wave
  2), 12 (ART-060, Rust sentences do not translate).

**Read the FAQ page before item 4 is designed**, per this document's own
"what was NOT read" section — and note that items 6 and 7 need the same
treatment: what `sd.unit0=ro` actually *means* to Emu68 has not been verified
from outside, and this project's most expensive rule is that a design must
not be built on recalled knowledge.

**One measurement taken since**: the Emu68 release on the owner's own disk
(`E:\amiga\ProjeART\emu68`) ships **no `cmdline.txt` at all** — 18 files, and
that is not one of them. So every token on that line is ART's to choose, which
makes item 7 a decision rather than a merge.

### 4. Identify install media by content, not by volume name

Today `core/osinstall/scan.rs` matches on the volume name inside the image, so
a **modified** `Workbench3.2` still answers `Workbench3.2`. Two things follow
from the imager's table that ART cannot currently see:

- **Escom ADFs are defective** — *"missing, among other things, language files
  (keyboard layouts too)"* — and the imager prefers Commodore/Cloanto. For a
  Turkish-facing tool, missing keyboard layouts is not a footnote.
- **DiskFlashback modifies ADFs**, enough to break identification.

ART's ROM table is the model to copy; the shape (`sha256`/MD5 + a friendly
name + a source + a per-release requirement) already exists in
`scripts/rom-table-check.py`.

### 5. Reconcile the RDB defaults — **two measured sources disagree**

| Field | ART | Imager | Note |
|---|---|---|---|
| Mask | `0x7FFFFFFE` | `0x7ffffffe` | **agree** |
| MaxTransfer | `0x0001FE00` | `0xffffff` | **disagree** |
| Buffers | 600 | 300 | **disagree** |
| Boot priority | 0 | 1 (System) | minor |

**Do not just take the imager's numbers.** ART's came from measuring the
owner's own cards — *"seventeen of them across three RDBs, without one
exception"* (ART-096) — which is stronger evidence than a default in somebody's
table. What is owed is a note in `rdb.rs` recording that the reference tool
writes different values and why ART's stand.

### 6. The default card layout

Adopt the reference default where ART has no measurement of its own: one FAT32
`EMU68BOOT` on `SD0`, one `0x76` area holding `SDH0`/`Workbench` (bootable) and
`SDH1`/`Work`. ART currently offers one partition and a `driveName` field.
**The 10-partitions-per-area cap is the imager's UI choice, not a format rule**
— do not copy it as one.

### 7. `cmdline.txt`

ART writes `sd.unit0=ro` with **one** prefix chosen from the Pi model; the
imager writes `sd.unit0=rw emmc.unit0=rw` — read-write, **both** families, so
one card serves a Pi3 and a Pi4. Decide `ro` vs `rw` deliberately (a
read-write boot partition is what the imager's own *Install* folder mechanism
needs) and write both prefixes unless there is a reason not to.

### 8. `.vhd` output beside `.img`

The imager offers both; a `.vhd` grows with its contents, so a 32 GiB card
image does not cost 32 GiB. Recognised by WinUAE and Windows. ART writes only
full-size `.img` — on a machine whose disk ART has already filled once.

### 9. AmigaOS 3.2.2.1 and 3.2.3 recipes

The media for 3.2.2.1 is **3.2's ADFs + the 3.2.2 updates + the 3.2.2.1
hotfixes**, and the hotfix package already contains 3.2.2's ADFs. ART's scan
assumes **one** folder. Either it learns to scan several, or it says what the
imager says — but a recipe that assumes one folder cannot express this release.
3.2.3 adds `Classes3.2.3`, `DiskDoctor3.2.3`, `Extras3.2.3`, `Locale-*3.2.3`,
`Update3.2.3`.

### 10. The package catalogue as data

[docs/amiga-package-catalogue.md](../../amiga-package-catalogue.md) lists 47
packages with sources; 41 are Aminet paths, which is the shape
`core/sources` already takes. A catalogue entry is a small JSON file — the same
"a fourth package is a JSON file, not a code path" rule the install recipes
already follow. Four entries carry licence constraints that must be answered
first (Picasso96, Roadshow, iBrowse, the two Cloanto CDN files).

### 11. Finish the OS Builder flow — wave 2

`describe_tree` landed early for [ART-199](../../ISSUES.md); what remains is the
artefact picker (a list of trees ART already built, showing **what each
carries**), splitting `OsInstall.tsx`, and deleting the duplicated ROM and card
fields. **Three of ART-197's four rows are still open.** Then wave 3 moves
*Verify against a card* off the install step.

### 12. [ART-060](../../ISSUES.md) — Rust sentences do not translate

For a suite whose reason for being bilingual is that its users are over fifty,

## Not on this list, and why

- **SFS support, whole-surface or read-only** — the owner's decision on
  2026-08-22, after this document's own research answered it. `ART-brief-sfs-integration.md`
  (outside the repo, deferral recorded at its head) asks for read + write +
  format through the `amiga-sfs` crate. SFS is a third-party filesystem for
  AmigaOS 3.x, the AROS default and part of 4.x — but the **Emu68 Imager
  installs PFS3 and not SFS**, which is the finding in this list's own
  catalogue work, and ART already writes PFS3 and FFS. The crate's 45 tests all
  run against data it produced itself, so nothing is yet known about format
  agreement; that needs the real SmartFilesystem handler, which is a bench
  session nobody has run. ART's honest `SFS — not supported yet` stays.

- **Reaching parity with the imager on RTG, networking or a bundled browser.**
  Item 10 makes those possible as catalogue entries; chasing them as features
  would starve what only ART does.
- **A first-boot hardware check like Buptest.** Worth wanting — ART's own rule
  is that a card is verified by something that is not ART — but it needs a card
  that boots first, which is item 1.
- **Anything from the 2021 retro32 guide.** That is the Raspberry Pi OS stack
  and does not apply to an Emu68 card.
