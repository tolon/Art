### 1. 🔴 A card flashed and an A500 booted

**SD-1's last item and the whole of ART's 1.0 bar.** Not code, and it runs in
parallel with everything below — but it is first because everything below was
written for it.

Nothing SD-1 or SD-2 has built has reached real hardware. What emulation has
settled is the **filesystem** side: a PFS3 volume ART formatted and an AmigaOS
3.2 tree ART built each boot a licensed Kickstart to a clean Workbench, so
`expansion.library` and the real `pfs3aio` binary have accepted ART's disk.
That is not provisional. What it does **not** touch is the card path — an MBR,
an Amiga disk starting 1.1 GB in, Emu68's `brcm-sdhc.device` and the FAT32
boot partition ([ART-095](../../ISSUES.md)'s shape).

The software side is complete and inventoried. **Only physical items are
missing**: a microSD card, a USB reader and an HDMI cable — the last plugged
in *before* power, or the VPU never configures the port and there is no RTG
that session.

**Done when** a card ART built starts an A500 and the machine is photographed
doing it, with the claim recording *which* machine.

### 2. 🔴 [ART-118](../../ISSUES.md) — the OS Builder's install screen, driven by a person

**The screen has never been seen past its own headings.** Deeper interaction —
filling the fields, ticking a component, running Plan or Verify — crashes the
renderer reproducibly with an access violation in every headless Chrome and
Edge combination tried, so this cannot be automated and has not been
substituted for.

It is second because of this project's own record: **the last time a screen was
driven by hand it immediately found two defects that 619 frontend tests had
not** — a refusal that protected data and said nothing on screen, and a verify
field labelled "Amiga volume image" with nothing to explain it. Tests are right
about the code and wrong about the world.

**Done when** the screen has been driven end to end against real material in
`pnpm tauri dev`, and every finding has a number.

### 3. ✅ A release update is layered, and ART can say so — **closed 2026-09-05**

*The whole of what is left of the old list's item 8. Not a JSON file — a
concept.*

**The next four paragraphs are this entry as it was written on 2026-09-04 and
are kept unchanged — they are the reasoning that opened the round, and two of
their claims were later corrected by measurement. What actually happened is
below them.** Read them in the past tense.

`extra_media_folders` is a **set**, and its refusal is right for one: two disks
of one name in folders somebody assembled are an ambiguity ART must not resolve
by click order. Measured on the owner's own material 2026-08-25: 63 volumes
across their 3.2.1 and 3.2.2 folders, and both carry a `DiskDoctor.adf` of
exactly 901 120 bytes under the same volume name with **different SHA-256s**.

So **a 3.2.2 install is refused today, correctly and uselessly** — with media
already in the owner's hands, which is what puts this above everything else
that is code.

What is missing is that "the base, then the update" is an **order the release
states**, not one the user clicked. Expressing it needs a concept ART does not
have, and inventing one under time pressure is how a design gets a shape nobody
can explain later.

**Done when** a layered source can be expressed and the owner's own 3.2.1 +
3.2.2 folders install without a refusal, with the later disk winning *because
it is later* and the log saying which one won and why.

**Closed 2026-09-05**, on `art-layered-release`, eleven tasks — with one part
of that sentence deliberately answered differently. A recipe declares ordered
media **layers** and may inherit another release's components, so `AmigaOS
3.2.2` is `AmigaOS 3.2` plus an update set; a component's media is resolved
inside the layer its recipe names. **The later disk does not win because it is
later — it wins because the recipe names its layer**, which is the stronger
answer: a list order is a click, a recipe is reviewable in a diff. The user
still supplies the ordering, by answering a labelled question per layer rather
than by the sequence they pressed "Add" in.

Three of this entry's own premises were corrected by measurement while it was
being built, and they are worth keeping:

- The refusal had **one** cause, not sixty. Across the owner's 3.2 and 3.2.1
  folders, 61 disks carry 60 distinct volume names; `DiskDoctor` is the only
  name Hyperion never versioned.
- **3.2.2 is cumulative** — its own `HowToInstall` requires "3.2 **or**
  3.2.1" — so the chain is base plus one update. This entry's "the base, then
  the update" was right; "3.2 → 3.2.1 → 3.2.2" would not have been.
- The two `Locale3.2.2` locales this entry names (CZ at 283 files, RS at 240)
  are confirmed, and they are two of seventeen locale components whose rule
  lists all differ — `-EN` carries `Help` alone, and only `-CZ`, `-RS` and
  `-RU` carry `Languages`.

Proved on the owner's own media: **4 052 files**, and the tree states
`Release 3.2.2`. Design and measurements:
[2026-09-04-layered-release-design.md](2026-09-04-layered-release-design.md),
[2026-09-04-layered-release-research.md](2026-09-04-layered-release-research.md).
**AmigaOS 3.2.1 is still not shipped as its own release**, and the reason is
the measurement above: 3.2.2 installs over 3.2 directly. For somebody holding
only 3.2.1 media it is one JSON file and no code.

The 3.2.2.1 and 3.2.3 recipes stay unwritten until their media is in hand — a
recipe written from volume names read off a web page is exactly how a tree that
was AmigaOS 3.5 shipped as 3.9 ([ART-159](../../ISSUES.md#fixed)).

*Carried into the design, and both held: the update ships two locales the base
set does not have (`Locale3.2.2-CZ` at 283 files, `Locale3.2.2-RS` at 240 —
whole locales, not overlays), and its own Kickstart is 47.111 with a
`HowToInstall` that recommends softkicking the modules rather than replacing
the ROM. That last sentence is why the Modules condition was built against the
ROM's resident table rather than its header.*

### 5. ✅ SD-2 G10 wave 2 — where `igame.data` goes — **closed 2026-09-05**

**The next four paragraphs are this entry as it was written on 2026-09-04 and
are kept unchanged — they are the reasoning that opened the round, and the
choice they framed turned out to be a false one. What actually happened is
below them.** Read them in the past tense.

**The last gap SD-2 names.** The format is done and verified against iGame's
own source (`core/gameindex/igame.rs`, 15 tests, eight mutations, eight fell) —
five of its six rules would have been got wrong by writing what the format
looks like from the outside.

But **"beside each slave" cannot be done for this collection**, and that is
measured rather than argued: 2 815 titles — 1 697 `whdload-hardfile`, 1 016
`floppies`, 102 `hardfile`, and **zero drawers**. The slaves are *inside* the
hardfiles.

Two routes, neither built, and they are not equivalent:

1. **Into the hardfile**, beside the slave, through `core/volume/write` —
   writes into the user's own image, so it is the mutation pipeline's full
   ceremony.
2. **Into a distribution's own Games drawer**, for a build that unpacks WHDLoad
   titles onto the volume ART is making — nothing existing is touched.

**Done when** one is chosen with a reason, built, and a real `igame.data` is
read by iGame — or, if the answer turns out to be neither, when that is written
down the way the AGS assessment was.

---

#### What happened — closed 2026-09-05

**The answer turned out to be neither, and the entry above is why.** Both
routes it offered write into WHDLoad **hardfiles**. iGame's own `examineFolder`
(`MrZammler/iGame`, `funcs.c`) walks the *Amiga* filesystem looking for `.slave`
files and reads `igame.data` out of the directory the slave is in — so a
self-booting `.hdf`, which keeps its slave inside the image, is invisible to it.
Route 1 would have written 1 697 files that nothing ever reads. The cost this
entry names — the mutation pipeline's ceremony, the free space those images have
left — was never the real one.

So the round did two things instead, on `art-whdload-drawers` (seven tasks):

- **Made the drawer shape exist in the catalogue at all.** "Zero drawers" was
  true of the *catalogue*, not of the world: ART could not read a drawer, so it
  found none. A directory holding one `.slave` is now a title
  (`core/gameindex/readers/drawer.rs`), and so is a drawer inside an `.lha`
  (`readers/lhadrawer.rs`), both reached from `store::refresh_root`. Measured
  against a real drawer collection: **893 found, 893 read back**.
- **Wrote `igame.data` beside a slave** — route 2 generalised. Into a tree ART
  builds, automatically and touching nothing of the user's; into a user's own
  collection only as an explicit action that previews, backs up and reports
  per entry.

**Still outstanding, and deliberately named:** no `igame.data` ART wrote has been
read by iGame on a real Amiga. That is the same bar as everything else here —
software proved, hardware not.

Three issues filed rather than patched at the end of a round:
[ART-242](../../ISSUES.md), [ART-243](../../ISSUES.md),
[ART-244](../../ISSUES.md). Design and plan:
`docs/superpowers/specs/2026-09-05-whdload-drawers-design.md` and
`docs/superpowers/plans/2026-09-05-whdload-drawers.md`.

### 6. 🟡 SD-5 G13 — the profiles half

`core/distro/registry.json` holds five entries — `caffeineos`, `coffinos`,
`amikit`, `art-baseline-32`, `art-baseline-39` — and **every one is
`available: false`**, which is checked and correct rather than pessimistic.
Three of them are somebody else's images, and ART may claim nothing about a
layout nobody has opened.

Below the items above because it cannot start without material: **ART never
downloads a distro image.** No URL list, no fetch button; the `homepage` field
is where the *user* goes, and ART then accepts the local file.

**Done when** a real distribution image has been obtained by the owner and read
by hand, its layout written into the profile, and one card planned from a named
distribution end to end.

### 7. 🟡 SD-3 G14 — wallpaper and prefs

G14 is "it is **mine**": wallpaper, WiFi, prefs and Startup-Sequence, each
edited in place. Two thirds are done — `startup.rs` edits `S:User-Startup` with
the `;BEGIN`/`;END` convention real installers use, and `core/amiganet/` closed
the WiFi and networking half against the owner's own stack's C source, with the
passphrase made unloggable by type rather than by rule.

**Wallpaper is new scope and is not designed.** Which picture formats, where
they go on the volume, what writes the prefs that point at them, and what
happens to a wallpaper the user already has — none of it is decided.

Last because the half that changes what ART can *do* is finished; this is the
half that makes what it builds look like the owner's own machine.

**Done when** the scope exists as a written design. Building it is a separate
item after that.

## How to use this file

Item 3 is closed (2026-09-05). Take item 1. Finish it to its **done when**. Update
[STATUS.md](../../STATUS.md), [ISSUES.md](../../ISSUES.md),
[FEATURES.md](../../FEATURES.md) and [session-log.md](../../session-log.md) as

rounds; items 5 and 7 are what is left of the build queue, in that order — **item 5 is the next build round**.

**Check the entry against the tree before building against it.** Writing this
file found a shipped feature marked "not started", a closed issue linked as
open in three documents, and a line count that had grown back by 151 lines. If
an entry turns out to be stale, correct it here in place with what was actually
found.

If an item turns out to be bigger than its place says, say so here rather than
finishing half of it quietly — a list that lies about size stops being usable
after about three items.
